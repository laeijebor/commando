Product shape

One cockpit, five jobs.

The MVP stays opinionated: it is a GUI for existing tmux state, not a replacement terminal, project manager, or hosted collaboration suite.

01 / NAVIGATE

Session switcher

Search, preview, attach, rename, create, and kill sessions without memorizing tmux commands.

  • Live windows, panes, cwd, branch, process, and attachment state
  • Fuzzy keyboard navigation and recent-session ordering
02 / ORGANIZE

Pane groups

Visual groups represent a feature cockpit: services, shells, editors, and agents move together.

  • Drag, resize, stack, float, collapse, and save named layouts
  • Every UI pane remains an actual tmux pane underneath
03 / ATTEND

Agent HUD

An attention queue, not another chat client: working, waiting, question, done, failed, or stale.

  • Status source is visible: hook, adapter, or heuristic
  • Jump directly to the exact pane that needs input
04 / CONNECT

Linear workbench

See assigned projects and issues, then bind a ticket to a tmux session, worktree, pane group, and notes page. Keep status changes fast and explicit; do not rebuild all of Linear.

05 / REMEMBER

Block notes

A local Notion-style editor with slash commands, autosave, backlinks, search, and first-class links to sessions, panes, commands, and Linear issues.

Inside MVP

  • Local-only web app
  • Attach to the current tmux server
  • Terminal I/O, pane management, saved groups
  • Agent attention events
  • Read-focused Linear view
  • Local notes with autosave

Deliberately later

  • Remote multi-user hosting
  • Full IDE/file editor
  • Replacing tmux or the user's shell
  • General agent orchestration framework
  • Full Linear issue administration
  • Cloud notes sync or team spaces
Proposed architecture

Browser polish, local authority.

A browser cannot safely access tmux, processes, or your filesystem directly. A small local daemon owns those capabilities and exposes a narrow event API to the React client.

AGENT STATUS CONTRACT

Reliable when instrumented, honest when inferred

Commando normalizes every provider into a small event model: working, question, done, failed, and stale. Provider hooks or wrappers emit high-confidence events; process/title/activity inspection is a clearly labeled fallback.

  • Event payload: provider, pane id, session, state, summary, timestamp, confidence, action target
  • Never parse or persist full terminal output by default; retain only bounded status metadata
SECURITY BOUNDARY

Local by default

  • Bind only to 127.0.0.1; use an ephemeral browser session token.
  • Store Linear credentials in the OS keychain, never SQLite or frontend storage.
  • Remote access is a later opt-in with explicit TLS/VPN guidance and authentication.
Delivery choice

Web first, desktop ready.

The UI should remain a web application even if it is later wrapped as a desktop app. This preserves fast iteration, responsive layout, and optional remote access without coupling the core to a shell.

ACCEPTANCE BAR

Performance and resilience

  • Initial session tree visible under 500 ms on a warm local start
  • Keystroke-to-pane echo targets under 50 ms locally with backpressure
  • Browser refresh rehydrates from tmux; it never kills or restarts panes
  • Daemon restart reconnects without corrupting tmux or saved layouts
PRIMARY RISKS

What deserves a spike first

  • Terminal throughput and resize correctness across many visible panes
  • Reconciling visual groups with tmux's tree-shaped native layouts
  • Agent completion/question detection without brittle output scraping
  • Multiple browser tabs issuing conflicting tmux mutations
