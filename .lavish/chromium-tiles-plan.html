A Chromium engine for web tiles — full CDP beside your panes

Web-pane tiles shipped with two renderers: a sandboxed iframe everywhere, and a native WKWebView in the desktop app. Neither is debuggable by agents. This plan adds a third, agent-choosable engine: a daemon-managed Chromium whose pages render into the existing tile chrome — so any agent (or you) gets real Chrome DevTools Protocol on the exact page you're both looking at: network inspection, request interception, breakpoints, performance traces.

Where we are, and the gap

Tier (shipped)Where it rendersHuman fidelityAgent debuggability
iframe (WebPaneCard.tsx) Every client — browser tabs, desktop app (localhost URLs) Native None — the user's browser (Dia, Safari shell) exposes no CDP
WKWebView (WebViewTileBridge.swift, commando.native-webview) Desktop app only, external origins Native None — WebKit's remote inspector needs private entitlements

The gap is one capability, in every client: nobody can attach a debugger to the page inside a tile. When my e2e drive "watched the tile", it worked only because I had launched my own Chrome with --remote-debugging-port — your everyday browsers don't expose that, and the desktop app's WKWebView can't.

Reframing from our chat. The question started as "Chrome instead of WebKit in the AppKit panes", and my first instinct was docking a real Chrome window into the grid. Working it through changed the shape: the AppKit app is not the only client missing CDP — all of them are. An engine owned by the daemon (not by any one client) fixes the gap everywhere at once, and sidesteps the window-juggling entirely. The docked-window idea survives below as a v2 fidelity upgrade, with its costs stated honestly.

The decision: how does Chromium get into a tile?

A · Headless Chromium + screencast tileRecommended v1

The daemon launches one managed Chromium (--headless=new, dedicated profile, loopback-only --remote-debugging-port) and opens one target per engine:"chromium" tile. The tile renders the page via CDP Page.startScreencast frames onto a canvas; clicks, scrolls, and keys relay back through Input.dispatchMouseEvent/dispatchKeyEvent. Agents attach to the same target for network/debugger/tracing.

  • Works in every client — desktop app, Dia, any browser, future remote access. One implementation.
  • Zero window management: frames are just pixels inside the existing tile chrome; masking/occlusion/z-order all keep working as today.
  • No new permissions; no bundled browser if we use an installed Chrome (Q2 below).
  • Human gets full DevTools too: the CDP endpoint serves the DevTools frontend — open it as a second tile beside the page.
  • Rendering is streamed frames: slight input latency, softer text than a native surface, no native text selection or ⌘F. Fine for a debugging surface; the WebKit/iframe tier stays the default for reading.
  • Continuous screencast costs CPU while the tile is visible (mitigate: pause frames when tile hidden or window blurred).
B · Docked real-Chrome window (AX puppeteering)Possible v2

Launch real Chrome with --app=<url> + debug port; the desktop app moves that window over the tile rect via the macOS Accessibility API, tracking every resize.

  • Perfect fidelity: it is Chrome — native scrolling, selection, extensions.
  • Requires the Accessibility permission for CommandoDesktop.
  • Cross-app z-order is not controllable via AX — the Chrome window floats; we can only hide it when Commando is occluded/behind. Spaces + fullscreen transitions need per-case handling.
  • Rect-only occlusion: the HUD drawer over a tile means hiding the whole window, not masking it.
  • Desktop app only — browser clients still get nothing.
C · Electron tile-host helperNot proposed

A small Electron app as companion window host: it connects to the daemon, receives tile rects, and positions its own frameless window (no AX permission needed). CDP via its debug port.

  • Self-positioning avoids the Accessibility permission.
  • Ships a second Chromium (~250 MB) + a second app to build, sign, notarize, update.
  • Inherits all of B's z-order/occlusion/Spaces problems — it's still a foreign window floating over the grid.
  • Desktop app only, again.
D · CEF embedded in the AppKit appRejected

Chromium Embedded Framework as a true in-process NSView.

  • Real embedded compositing — the only option where Chromium is a first-class view.
  • ~250 MB framework, C++ integration surface with poor Swift ergonomics, our own Chromium security-update treadmill, notarization + multi-process packaging complexity. Permanent heavy maintenance for a lightweight local cockpit.
  • Desktop app only.

The load-bearing property: agent and human share one page. The agent's Network.enable, breakpoints, and Page.navigate act on the same target whose pixels you're watching in the tile — true co-browsing, with the daemon as the single owner of the browser process.

Security model. A CDP endpoint is total control of the browser it belongs to, so: the debug port binds to loopback only; the profile is a throwaway under ~/.commando/chromium-profile/ (never your personal browser profile — no cookies or sessions to steal); discovering the endpoint requires the existing agent hook token (timingSafeEqual, same as tile opens); and the trust policy is unchanged — an external origin still pends until you confirm, before the Chromium target ever navigates to it. Note Chrome ≥136 itself refuses --remote-debugging-port on a default profile, so the dedicated --user-data-dir is mandatory anyway.

Protocol & API changes

Additive throughout; every existing tile keeps working with engine defaulting to 'webkit' (today's iframe/WKWebView pair).

// shared/protocol.ts — WebPane gains one field
export type WebPaneEngine = 'webkit' | 'chromium'
export type WebPane = {
  /* …existing fields unchanged… */
  engine: WebPaneEngine          // default 'webkit'
  cdp?: { attached: number }     // broadcast so tiles can show "1 agent watching"
}
# Agent surface — open a debuggable tile, then discover its CDP endpoint
curl -X POST :4310/api/web-panes \
  -H "Authorization: Bearer $(cat ~/.commando/agent-hook-token)" \
  -d '{"url":"http://localhost:8081","anchor":"%22","engine":"chromium"}'
# → { ok, webPaneId: "w-4be1c2", status: "open", engine: "chromium" }

curl :4310/api/web-panes/w-4be1c2/cdp -H "Authorization: Bearer …"
# → { browser: "ws://127.0.0.1:9223/devtools/browser/…",
#     target:  "ws://127.0.0.1:9223/devtools/page/ABC123",
#     devtoolsFrontendUrl: "http://127.0.0.1:9223/devtools/inspector.html?ws=…" }

# chrome-devtools MCP attaches straight to it:
#   chrome-devtools-mcp --browser-url http://127.0.0.1:9223
  • scripts/commando-open grows --engine chromium; the ⌘K palette command and the Ports panel get an "open debuggable" variant.
  • show-in-commando skill: new section — default to webkit for showing things; choose chromium when you intend to debug (network, breakpoints, tracing); fetch /cdp and attach.
  • Tile chrome: engine chip (chromium), "n agents attached" in the footer, 🛠 DevTools action.

Build plan

  1. Engine core (daemon). server/chromium-engine.ts: locate/launch the managed Chromium, per-tile target lifecycle, crash + restart handling, teardown of orphaned targets in prune(). engine field through shared/protocol.ts, web-panes.ts, API validation, persistence (a restored chromium tile relaunches its target lazily). Unit tests with a stubbed CDP.
  2. Screencast tile (all clients). Daemon WS relay (/ws/web-tiles/:id, owner-cookie auth) bridging screencast frames out and input in. ChromiumTileCard in the web client: canvas rendering, coordinate mapping, wheel/keys, pause-when-hidden. This is the phase with the feel-risk — gate on a fidelity check: type into a form, scroll docs, drag-select; decide frame quality/fps knobs here.
  3. Agent surface. /cdp discovery endpoint (agent token), cdp.attached broadcast, commando open --engine, skill update in all three installs, DevTools-frontend tile action. E2e on the isolated stack: agent opens a chromium tile, attaches via chrome-devtools MCP, watches a request the human's click triggers.
  4. Merge gate. npm run typecheck + vitest + Swift tests (untouched paths still green) + the e2e drive above + dogfood on the live stack (a real debugging session on a real dev server).

Worktree ../commando-chromium-tiles, branch chromium-tiles, vault note updated as phases land — same workflow as the web-panes build.

Risks & open questions

RiskSeverityMitigation
Screencast feel disappoints for interactive use (latency, soft text, no native selection) Medium Phase-2 fidelity gate before building further; PNG frames + devicePixelRatio-aware sizing; if it fails, option B (docked Chrome) is the fallback and this plan's daemon/CDP layers are still the substrate it needs.
Chromium discovery: user has no Chrome installed, or an incompatible one Medium Q2 below — probe Chrome/Chromium/Edge/Brave paths, else offer a pinned Chrome-for-Testing download on first chromium tile.
CPU cost of continuous screencast on a laptop Low Stream only while the tile is on-screen and the client focused; drop to on-demand stills otherwise. Headless Chrome idles cheaply.
Agent misuse of CDP power (navigate the tile somewhere external un-confirmed) Medium Daemon watches Page.frameNavigated on tile targets: a main-frame navigation to a non-allowlisted external origin blanks the screencast and flips the tile to the existing pending-confirm card. Q3 decides how raw the agent's pipe is.
Managed Chromium lifecycle leaks (orphan processes after daemon crash) Low Process-group kill on exit; PID file + startup sweep; targets are cheap to recreate from persisted tile state.
