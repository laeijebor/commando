Recommendation

Build a small "farm" service. It is a lease queue taken out of Commando, plus one host gateway that only lets you reach the devices you hold. Interactive agent work goes through Argent's own remote tool-server behind that gateway. Your laptop agent keeps the same MCP tools it already uses; only the URL changes. Measurements run as jobs on the host: you upload builds and a plan, the host runs repeated, interleaved A/B rounds, and you get results.jsonl plus traces back. Raw adb through the gateway is the Android escape hatch. A host agent is optional, for diagnosing failures, not for running measurements.

Approving this means a new repo, a lease API with a different identity model than tmux panes, and Commando keeping its local queue as a client of the farm.

Why, in one line each

  • B (MCP on host) mostly exists already. Argent ships argent server start plus argent link. Over that link it uploaded my 230 MB APK and brought the Perfetto trace back to the "laptop" on its own. It has no idea of tenants, so it needs a lease gateway. I built one in about 80 lines and it works.
  • C (raw CLIs over Tailscale) works for Android and can be made safe with an adb-protocol gate. It can't work for iPhones: devicectl and xctrace only talk to devices attached to the Mac they run on.
  • A (host agent runs the workload) was the slowest, most expensive and noisiest. The same 5× cold-start job took 188 s and $0.30, and it accidentally ran two launches at once. A 10-line script took 51 s with a spread 4× tighter.
  • Jobs match how you already profile (plans/*.txt × variants → results.jsonl). Jobs keep running when a laptop sleeps. And no laptop round-trips sit inside the measured window.

Goal and constraints

Users
~7 product engineers, each running Claude Code or Codex agents on their own laptop.
Hosts
One or more always-on Macs with physical Android phones and iPhones plugged in by USB.
Main use
Performance profiling of the React Native app: CPU % per thread, cold start, jank and frames, memory, Perfetto / simpleperf / xctrace / Hermes.
Secondary
Smoke-testing a native module on a real device; driving the app interactively.
Network
Probably Tailscale, so we can use tailnet identity (tailscale whois) and ACLs.
Like today
"Similar to what I do locally": lock → install variant → deep-link ablation → record N s → analyse → append to results.jsonl → restore the standard app → release.

What today's queue already gets right (keep it)

  • One ordered queue per resource, with any-android / any-ios selectors and named devices when results must be comparable.
  • Agents get an offer and must claim it within 5 min; scripts block (--wait --pid). Re-locking is idempotent, and you're dropped after 3 missed turns.
  • Release steps attached to each device ("restore a2, log in NOTES.md"), a Devices view for pausing, reordering and force-releasing, and heavy busy-process detection.

What's tied to one machine (has to change)

  • Identity is a tmux pane id (%79) plus --as plus --pid. A laptop agent has none of these on the host.
  • Liveness is "pane exists / pid alive", checked on the host. A remote client needs a heartbeat TTL instead.
  • Offers are typed into the agent's tmux pane. Remote clients need long-poll or SSE, and Commando can relay into the pane as one such client.
  • One shared hook token on localhost. The farm needs a per-engineer identity.

Discussion with Sol (Codex, GPT-6.1)

Two rounds. Round 1 was blind: it got the code and your three options. Round 2 got the trial results and my draft, and was asked to attack it.

Round 1, before the trials

  • Same shape as mine: "Build a host job runner with a thin MCP interface and an interactive lease mode." Upload → queue → prepare → run N → analyse → clean → publish.
  • On A: "use a host agent to author scenarios and investigate failures. Execute measurements through deterministic tools." The trial backed this up.
  • On C: Android is viable but adb reverse ends at the host; iOS should stay on the host, with direct CoreDevice forwarding "uncertain". Also matched by the trial.
  • Measurement hygiene: no heavy builds during captures; gate on battery, thermal and charging; record OS, refresh rate and brightness; interleave baseline and candidate on the same phone; separate "diagnosis" runs (Metro/Hermes) from "benchmark" runs (bundled JS).
  • Extraction: keep the scheduler, selectors, offers, idempotency and withdraw-after-grant, plus their tests. Replace LockOwner, the pane/pid sweeps, pane-message delivery and the shared token. Use SQLite and don't share the JSON file across hosts.

What it missed: that Argent already covers iPhone driving and remote upload/download. It suggested Appium/WDA for iOS interaction.

Round 2, after the trials

Sol's headline: "Build a small profiling appliance first… device recovery will probably consume more effort than queue scheduling."

Where Sol agreed

  • Take the host agent out of execution. Front Argent rather than reimplementing its device tools. Keep adb as an escape hatch. Use bundled JS for benchmarks and live Metro only for diagnosis.

Where Sol pushed back (and I think it's right)

  • Checking device ids isn't enough. The gateway needs an explicit tool allow-list. run-sequence and flows run nested actions; profiler stop and artifact handles have no device argument; and a check when a request is admitted can't revoke a capture that's already running. I've added this to the risks.
  • The adb gate only reads the first frame. Unknown requests pass, and forwards are host-wide even for an authorised serial. Production needs a protocol allow-list or state machine, live revocation, and forwards owned by the lease.
  • iOS: registered recipes, not arbitrary scripts. Make measure.sh a versioned host recipe with validated parameters. ForceCommand or a separate macOS account per lease is not a real sandbox, and whether it isolates Instruments sessions is unproven.
  • Release needs a cleanup state. Today's registry releases and immediately offers to the next request. The farm needs revoke → stop → clean → verify → reassign, and it must reconcile after a crash.
  • Pin Argent versions. Sol's read of the newer docs: flows are now "E2E tests", and linked CLI runs are documented in later versions, so my "flow run refuses remote" finding may be specific to 0.26. You have 0.26; 0.32 is out.
  • The decisive next trial is a wired iPhone running your real variant × ablation plan through measure.sh remotely, including disconnect, cancel and cleanup. The emulator plus am start -W proves the plumbing works, not the measurements.

Where we disagree: what v0 is

  • Sol: v0 is the job appliance. Uploaded artifacts plus a plan, run unattended, with one active farm session per Mac, polling only, and no MCP, SSE or Commando integration yet. It gets the numbers right first.
  • Me: v0 is the lease + Argent gateway, because your engineers' first need is "my agent can use a real phone at all", and that is almost free. Jobs follow in v1. I would limit it to one capture per host at a time rather than one session, so interactive leases on different phones can still run side by side.

  • The lease service is the only authority. It holds who holds what and who is queued, plus offers, heartbeats and health. Commando's DeviceLockRegistry moves here almost unchanged, with a new owner identity.
  • The gateway is the only door to the devices. Every request carries a tenant identity (tailnet whois plus a session id). Every device-targeted call is checked against current leases, and listings are filtered. The spike already does this for Argent and adb.
  • The job runner takes a lease itself, gates on health, runs the plan, cleans up (restores the standard app), releases, and publishes results.
  • Commando becomes a client. Your local Devices view shows farm devices next to local ones, and offers still appear in the pane.

  loop while working
    A->>F: heartbeat (every 30s)
  end
  A->>F: release
  F->>F: run release steps (restore app)
  F-->>A: released
  • A heartbeat replaces pane/pid liveness. The CLI and MCP adapters send it automatically. A missed TTL triggers cleanup before the next offer.
  • Offer delivery uses long-poll or SSE from the farm. Commando subscribes and keeps typing "Pixel 5 is yours…" into the pane, so today's agent UX survives.
  • Release steps become automatic where possible: the host reinstalls the standard app itself instead of trusting each agent to.

What an engineer's agent actually does

One-time setup

brew install tailscale && tailscale up      # join the tailnet
npx @company/farm init                        # adds MCP entry, skill, sets ARGENT_TOOLS_URL

Interactive (debugging and poking around)

farm lock pixel --task "check shop jank"      # queued → offered → held (heartbeat in background)
# the agent's normal Argent MCP tools now hit the farm's Pixel:
#   reinstall-app (uploads APK) · launch-app · describe · gesture-tap · native-profiler-start/stop
adb -s 25121FDD4S00H7 shell dumpsys gfxinfo …  # optional: raw adb through the gate
farm release pixel

Measurement (what you'd run for an A/B)

farm job submit \
  --device pixel --artifact base=a2.apk --artifact fix=cp3-all.apk \
  --plan plans/android-p5.txt --iterations 5 --interleave \
  --measure "cpu:main,js,RenderThread" --settle 15s --duration 45s
# → job 7f3c queued (#1 on pixel)
farm job wait 7f3c    # streams progress; laptop may sleep
# → results.jsonl (per run), summary.md (median/IQR per variant), traces/ (download on demand)

The plan format can start as your existing plans/*.txt (variant, ablation spec, deep link). Argent flows would be added later for scenarios that need taps.

iPhones specifically

  • Everything runs on the host: devicectl, xctrace and Argent's iOS tools need the phone attached to the Mac running them. No laptop-side CLI path exists.
  • Builds: laptops (or CI) build a signed device .app/IPA. The provisioning profile must include the farm phones' UDIDs and get-task-allow for profiling. Upload it the same way the APK went up.
  • Your xctrace scripts (measure.sh-style) become a job type: "run this script under my lease on the host", with only the leased device id in env, in a per-job temp dir, as a non-admin farm user. That's the iOS escape hatch, the equivalent of the adb gate.
  • Phones must stay cabled (Argent refuses Wi-Fi iPhones), and the host should keep them awake and unlocked (no passcode on farm devices).

Making numbers comparable across people

  • Health gate before every offer and every job iteration: screen unlocked, battery ≥ 50 % and charging policy, thermal state nominal, cabled, no heavy build running on the host.
  • Record the environment on every result row: device, OS, refresh rate, brightness, thermal and battery, host load, artifact hash.
  • Interleave A/B on the same phone (ABAB…, not AAAA BBBB), with a cooldown between runs. That's how the job runner orders iterations by default.
  • No heavy builds on the host during capture. heavy stays a lock, and the job runner holds it while recording.
  • "Benchmark" vs "diagnosis" runs: benchmarks use bundled-JS release-like builds with no Metro; diagnosis (Hermes/React profiler) is interactive and isn't comparable.

Risks

The gateway only sees tool names and arguments. Sessions, run-sequence and flows (nested actions), profiler-stop and artifact handles, or tools with no device argument could act on a device you don't hold. A check when a request is admitted also can't stop a capture already running. Mitigation: allow-list tools rather than block-list them, block run-sequence and flows until they're validated, scope artifact ids per tenant, keep upstream Argent on loopback with its token held only by the gateway, and add a contract test per Argent upgrade. Expiry must revoke, stop and clean up.
The spike checks only the opening request. Production needs a protocol allow-list, revocation of live connections when a lease ends, and forwards/reverses owned by the lease and torn down on release. Ship it behind an experimental flag.
Today's registry offers the device to the next request the moment it's released. A crashed run leaves a test build installed (your LOCKS.md already warns about this). Add a cleaning state: revoke → stop → restore the standard app → verify → offer.
The laptop runs argent mcp 0.26 against a host on 0.32, and the upload format or tools drift apart. Mitigation: the gateway reports the host version, and farm init pins the client to match.
Not exercised today because the phone was on Wi-Fi. Mitigation: make a wired iPhone run the first task of v0, before building on it.
Your APKs are about 230 MB (126 MB compressed). Over home Wi-Fi to the office, that's roughly 30–60 s per variant. Mitigation: content-hash dedupe, so an unchanged base is uploaded once.
Other tenants' installs and the emulator compete with captures. Mitigation: the job runner holds heavy during capture, keep emulators off farm hosts, and record host load.
