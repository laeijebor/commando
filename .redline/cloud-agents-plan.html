Implementation plan · skeptical review incorporated · round 2

Cloud work that survives a closed laptop

Add a durable Cloud tasks area using the official, subscription-backed Claude Code and Codex CLIs. After a provider accepts a task, execution no longer depends on Commando or the laptop staying awake.

Approval means start implementing this plan with parallel subagents, fixture-based verification and dependency setup in the isolated feature worktree. Live provider tasks need a separately identified authenticated provider and disposable target.

01 · A focused first release

  • Cloud tasks beside Workspace, Linear and Notes: create, list/detail, explicit linking, archive/unarchive, provider link, refresh, delivery diagnostics and supported results. Available with zero tmux sessions.
  • Codex: configured environment/ref, tracked-task reconciliation with official list/status, on-demand read-only unified diff. Follow-up stays in the provider UI.
  • Claude: supported repository-context submission, receipt-acknowledged follow-up, provider UI for live status. No native transcript or authoritative background status.
  • Workspace HUD: a compact separate Cloud tasks group. Existing local filters/counts and workspace selection stay intact.
  • Durability: local task/operation journal, restart/wake recovery, independent execution and observation health, capability/readiness checks per provider.

Milestone 1: prove one enabled provider’s create → receipt → detached execution → recovered detail/link. Milestone 2: HUD, archive, diff polish and the second provider. These remain release scope, not prerequisites to proving the core path.

Deferred boundaries

SSH/Herdr, an owned always-on machine, managed-agent APIs and API billing, mobile/Island changes, arbitrary cloud tiles, full transcripts, unsupported cancellation, local patch apply/checkout/merge, automatic upload/push, scheduled multi-step orchestration, importing all account tasks, and multi-account/profile management.

Store only tasks submitted or explicitly linked through Commando. Closing a tile or archiving a task changes local presentation, never remote execution. No publishing, merging or applying provider changes accompanies submission.

Claude Routines’ limited trigger API and the separate managed-agent APIs remain research context, not this release’s integration. Claude teleport/resume and local Remote Control do not establish ongoing cloud execution.

04 · Local intent is not cloud acceptance

Recorded locally → Sending → Submitted to Claude/Codex. Only the final state has a valid provider receipt. Until then, do not tell the user it is safe to close the laptop. An HTTP 202 is only a durable local acknowledgement.

SituationWhat the interface says and does
Claude accepted“Submitted · Live status in Claude.” Restore receipt/link on wake; no pretend polling or completion state. A valid follow-up acknowledgement says “Message sent.”
Codex observedMap queued/running/needs-input/result-ready only from supported evidence. Keep raw bounded status. “Result ready” is review availability, never a claim of passed tests.
Create may have happened“Delivery unknown — check provider before retrying.” Explicit linking can recover task identity, labelled user-supplied if unverifiable. No replay; a list miss or prompt/time similarity proves nothing.
Follow-up may have arrivedKeep that message delivery_unknown until message-specific receipt evidence exists. Linking its session never proves message delivery. “I checked” is separate user metadata, not provider confirmation.
Client offline / staleKeep cached status and last-checked time. Disable daemon mutations, retain provider links. Reconnect without focus theft; a sleeping client is not an agent failure.
Source preparation is explicit

Provider → repository context/environment + branch → prompt → destination summary → submit. Codex uses an existing configured environment; allow manual environment ID when no documented machine-readable discovery exists.

Claude requires a clean, pushed GitHub source, but clean git status or a scratch checkout does not prove no bundle upload. Creation stays disabled unless P0b establishes a supported, enforceable source-selection/no-bundle path. No automatic push. Record requested ref/commit where knowable without claiming an immutable remote commit for a moving branch.

Freeze the confirmed repository/remote/ref with the intent; revalidate immediately before dispatch. Drift or unenforceable policy means no dispatch and reconfirmation. Test ignored/untracked secret-like files and alternate remotes.

P0 chooses scratch ownership or a short-lived preparation lease only for checkout lifetime, not upload-policy proof. After acceptance, neither checkout nor local submitter is required. Origin deletion and recycled pane IDs cannot delete or rebind cloud identity.

Journal ordering, duplicate handling and restart rules
  1. Validate capability, source, bounds and key. Record an immutable canonical intent before spawn.
  2. Same key/hash returns the original operation; same key/different hash returns 409. Claim with a dispatcher runtime UUID and live-owner lease/heartbeat; another service cannot recover active work.
  3. Persist dispatching before invoking the CLI. Capture a valid receipt early and persist receipt + remote task identity atomically. A receipt remains acceptance evidence even if a later local step fails.
  4. Only proven pre-dispatch validation/spawn failure can be rejected outright. After possible dispatch, timeout/nonzero exit/malformed receipt may mean delivery_unknown.
  5. Only abandoned dispatching becomes unknown, conditionally on owner-liveness/epoch checks. Lease expiry never permits redispatch. Restarted prepared intents await user account/source reconfirmation.
  6. Append late receipts as evidence and reconcile conditionally: a matching identity upgrades verified state; a conflict with manual linking is surfaced without overwriting either identity.
  7. Create recovery may verify/link identity; a new create requires a new intent and duplicate-risk acknowledgement. Message recovery requires its own receipt evidence, never a session link or user acknowledgement.

Guarantee: durable local deduplication and no blind replay. Exactly-once remote creation needs provider cooperation and is not promised.

Browser recovery · retain the key before POST

Generate a UUID key and freeze the payload in memory before POST. Persist only key + canonical request digest + installation scope in a small pending-intent index—no prompt or credentials. Transport retries use the same key and frozen payload.

After reload, look up the operation by key before enabling resubmission. If received, the daemon’s immutable payload is authoritative. If not found, do not replay: restore/re-enter and reconfirm; reuse the key only with a matching digest. A changed draft explicitly creates a new intent.

Accepted/unknown operations remain discoverable in a recovery view after browser-storage loss. Clear pending keys only after outcome reconciliation; never silently hide unknown operations.

05 · Separate identity, shared observation

Typed HTTP operations and a shared stale-aware client store feed detail and HUD. A protected service owns delivery; provider execution continues independently of polling. No expansion of tmux snapshots or new WebSocket event family in v1.

Reuse boundaries and observation policy
  • Reuse named-client/stale-data patterns in src/prsApi.ts / src/prStore.ts, injected runner/single-flight patterns in server/prs.ts, and AuthService / createNetworkAccess boundaries. Do not use runCommand: shell spawn is not remote acceptance.
  • TmuxSession, AgentStatus, SessionBrief and CompanionSession remain local. Cloud records stay outside refreshSnapshot() pruning and removeMissingSessions.
  • One server-side single-flight observer per provider/context caps CLI work across viewers. Codex active tasks refresh at roughly 30-second foreground intervals, immediately on focus/online/reconnect, with exponential backoff/jitter and no wake catch-up burst. Selected detail and HUD share one client store.
  • Claude observation restores its receipt/link only until a read capability is verified. Do not make execution dependent on polling.
  • Diff is escaped, on-demand plaintext, capped at 256 KiB or 5,000 lines, with truncation and provider link. Reuse git-diff.css typography, not pane-bound GitDiffModal fetching.
Proposed contracts, persistence and routes

shared/cloud-tasks.ts defines capability flags for create/link/list/inspect/sendMessage/diff/accountIdentity, readiness reason and tested CLI version. Task records include local UUID, provider/context/account identity when verified, remote ID/URL, prompt/title, source/ref/commit, historical origin, remote/raw state, observation health/timestamps, revision, results and archive time.

Operations hold UUID/task ID, create/message/link kind, key + canonical request hash, immutable payload, safe receipt, timestamps and bounded error code. States: prepared / dispatching / accepted / rejected / delivery_unknown. Execution, observation, process exit and provider outcome are distinct.

Dedicated private-permission ~/.commando/cloud-tasks.sqlite, test override COMMANDO_CLOUD_TASKS_PATH. Reuse DatabaseSync from server/auth.ts, separate from auth DB. Migrations and transactional updates; corruption blocks mutations, never resets. Keys persist with operations, scoped by installation/owner; remote IDs by provider/context. An unverified context is only a local namespace, not cross-account deduplication. No destructive history cleanup.

Owner authorization and subprocess boundary

All cloud routes sit behind requestIsAuthorized using the owner cookie or daemon token; hook-only access gains no cloud mutations. Preserve provider auth stores and store only a non-secret context ID plus official account identity where exposed. An unchanged config path is not account identity.

If inspectable, recheck identity immediately before mutations and block mismatches. Otherwise label it unverified and require explicit current-account/context confirmation for each saved-task mutation and recovered prepared intent; no automatic resume after restart. User-declared account changes create a new local context generation, suspending old tasks until reconfirmed. This user check does not promise detection of external switches.

Fixed executable/argv, shell:false, bounded output/timeouts, sanitized errors and deliberately constructed subprocess environment. Preserve required auth/config/PATH behavior while stripping unrelated Commando credentials. No HTTP executable/argv/env/URL-to-fetch fields, OAuth-token copying or private task APIs. Validate provider links against documented origins and encode route IDs. No automatic login on discovery failure.

Prompts/history receive owner-level access protection. Raw credential output never enters storage; detailed diagnostics are bounded and demand-loaded. Provider HTML and raw diagnostics never go directly into the DOM.

07 · Verify the failure paths before release

All implementation and release gates remain open. Fixture success establishes local behavior; live evidence establishes provider support.

  1. Real subprocess fixtures: assert argv/cwd/env, bounds/timeouts and parsing through fake executables. Unit/e2e never reach real providers or read actual credentials.
  2. Durable delivery: crash windows and lost-202 + browser reload recover the same key/operation without duplicate dispatch. Concurrent keys dispatch once locally; ambiguous creates/messages are not replayed.
  3. Owner races + message evidence: a second daemon cannot recover a live dispatcher; late receipts confirm identity or expose linking conflicts without overwrite. Session linking and “I checked” never mark an uncertain message accepted.
  4. Source + account: ignored/untracked secret-like files, alternate remotes and post-confirmation drift block dispatch when policy is unenforceable. Account replacement at the same config path invokes verified mismatch handling or explicit unverified-context reconfirmation.
  5. Failure + lifecycle: malformed/large output, missing CLI, auth expiry and rate limiting retain cached truth. Zero tmux, worktree deletion and recycled IDs never delete/rebind cloud records.
  6. Real authorization: owner/token/Origin cases through actual route composition; hook credentials cannot create/message/link. Corruption blocks mutations.
  7. Shared observations: clock jumps, focus, visibility, online/reconnect and multiple viewers remain bounded. No catch-up burst, focus theft, phantom completion or offline failure.
  8. Real App/CSS browser flow: desktop, 390px and breakpoint edges; modal focus trap/restoration, keyboard, reload, unknown recovery, escaped/truncated diff, provider links, archive and local navigation regression.
